## Development Environment Setup

### Prerequisites

- Node.js (v18 or higher)
- PostgreSQL (v12 or higher)
- npm or yarn

### Installation Steps

1. Clone the repository

   ```bash
   git clone git@github.com:hngprojects/deenAI-BE.git
   cd deenAI-BE
   ```

2. Install dependencies

   ```bash
   npm install
   ```

3. Setup environment variables

   ```bash
   cp .env.example .env
   # Edit .env with your configuration
   ```

4. Build the application

   ```bash
   npm run build
   ```

5. Run database migrations

   ```bash
   npm run migration:run
   ```

6. Start development server

   ```bash
   npm run start:dev
   ```

7. Access API documentation at: `http://localhost:PORT/api/docs`

## Configuration Details

### Environment Variables

Required environment variables:

```bash
# Application
PORT=6001
NODE_ENV=development

# Database
DB_TYPE=postgres
DB_USERNAME=your_username
DB_PASSWORD=your_password
DB_HOST=localhost
DB_PORT=5432
DB_NAME=your_database
DB_ENTITIES=dist/modules/**/*.model{.ts,.js}
DB_MIGRATIONS=dist/database/migrations/*{.ts,.js}
DB_SSL=false

# JWT
JWT_SECRET=your_secret_key
JWT_TIMEFRAME=3d
```

### Database Configuration

- Uses PostgreSQL as the primary database
- TypeORM for ORM with SnakeNamingStrategy to convert camelCase to snake_case
- Database synchronization is disabled (uses migrations instead)
- Automatic migration running on application startup

### API Configuration

- Global prefix: `/api/v1`
- Swagger documentation available at `/api/docs`
- CORS enabled
- Trust proxy enabled
- JWT authentication with Bearer token

### Testing

- Unit tests using Jest
- E2E tests configuration available
- Test coverage reporting supported
- Separate test environment configuration

## About DeenAI

DeenAI is a warm, intelligent, and faith-centered digital companion designed to help Muslims build a peaceful, consistent, and emotionally supportive relationship with the Qur'an. It brings together AI-guided reflections, a clean Qur'an reading experience, and essential daily worship tools—all in one calming, distraction-free space.

### Key Features

1. AI-Powered Qur'an Chat with Qur'anic references and explanations
2. Immersive Qur'an Reader with Uthmani script and translations
3. My Reflections - Private encrypted journaling with linked ayahs
4. Prayer Times & Reminders with accurate timings
5. Tasbih - Simple counter with persistent state

## Git Workflow

### Branch Structure

- Follow the existing branch structure (develop branch exists)
- Create feature branches from `develop`
- Use descriptive branch names (e.g., `feature/user-authentication`, `fix/email-validation`)

### Commit Guidelines

1. **Commit Regularly in Small, Logical Units**
   - Each commit should represent a single, self-contained change
   - Stage changes before committing: `git add <files>` or `git add -p` for partial staging
   - Make atomic commits - if you need to describe multiple things, it should be multiple commits
   - Commit often: small, frequent commits are better than large ones
   - Review before committing: use `git diff` to review changes

2. **Commit Message Structure**

   Follow the Conventional Commits specification (https://www.conventionalcommits.org/):

   ```
   <type>[optional scope]: <subject>

   [optional body]

   [optional footer(s)]
   ```

3. **Commit Types**
   - `feat`: New feature for the user
   - `fix`: Bug fix
   - `docs`: Documentation changes
   - `style`: Formatting, missing semicolons, etc. (no code change)
   - `refactor`: Code refactoring (no functional changes)
   - `perf`: Performance improvements
   - `test`: Adding or updating tests
   - `build`: Changes to build system or dependencies
   - `ci`: Changes to CI/CD configuration
   - `chore`: Maintenance tasks (updating dependencies, etc.)
   - `revert`: Reverting previous commits

4. **Commit Message Rules (DO)**
   - ✅ Use imperative mood: "add feature" not "added feature"
   - ✅ Keep subject line under 50 characters (hard limit 72)
   - ✅ Start subject with lowercase (after type)
   - ✅ Separate subject from body with blank line
   - ✅ Wrap body at 72 characters
   - ✅ Use body to explain **what** and **why**, not how
   - ✅ Reference issues in footer: `Closes #123`, `Fixes #456`
   - ✅ Use present tense

5. **Commit Message Rules (DON'T)**
   - ❌ Don't end subject line with period
   - ❌ Don't use past tense
   - ❌ Don't be vague: avoid "fixed stuff", "updated code"
   - ❌ Don't combine multiple unrelated changes
   - ❌ Don't include unnecessary details in subject

6. **Best Practices**
   - Test your code before committing
   - Commit working code - don't commit broken builds
   - Write commit messages as if explaining to a teammate who will read them in 6 months
   - Use the body to provide context that isn't obvious from the code
   - Reference related issues and pull requests
   - For complex features, break into multiple small commits

7. **Team Conventions**
   - Use consistent scope names across the team
   - Always link commits to issue tracker when applicable
   - Communicate breaking changes clearly in commit footer
   - Review commits during code review for message quality
